# Content model checklist

These checks form the AI pass for the `contentModel` dimension. Run every check in this file against the target repository. A check fires a finding only when its "Pass when" criteria objectively fail — when the evidence is ambiguous, don't fire the finding; note the uncertainty in the report narrative instead (see the determinism rule in `grading.md`).

One check here (`AUD-CM-005`) interprets Sentinel's own `CNT001` finding in context rather than restating a fixed pattern match; the rest apply Xperience by Kentico content-modeling conventions Sentinel's static rules don't check at all. Several checks (`AUD-CM-004`, `AUD-CM-005`, `AUD-CM-007`, `AUD-CM-009`, and part of `AUD-CM-010`) touch data that only a database or the Management API can confirm — folder/workspace placement, language-variant completeness, published URL slugs, asset folder organization. This audit runs either with a Sentinel runtime scan (`report.json` produced with a connection string, so `scan.runtimeEnabled` is `true` and rules like `CNT001`/`CNT002` carry real findings) or static-only (no connection string, `scan.runtimeEnabled` is `false`). Where a check depends on that kind of evidence, it's split into a repo-only criterion — the only basis on which the check may fire — and an environment-dependent part that's informational only and reported as "unverified" when the evidence isn't available, the same way `architecture-config.md` and `security.md` handle their own environment-dependent checks. The one exception is `AUD-CM-005`: the `CNT001`/`CNT002` data it depends on already lives in the scan artifact by the time this audit runs, so that data counts as always-evaluable repo-adjacent input, not a live probe that might be unreachable — see that check for the narrower caveat that still applies (a static-only scan never produced the data at all).

### AUD-CM-001: Shared content lives in reusable content types, not duplicated page fields

- **Inspect:** Field definitions across `PageContentTypes/*/*.generated.cs` (or the project's equivalent page type classes) and `ReusableContentTypes/*/*.generated.cs`. Look for the same logical content — a person's bio, a product description, a testimonial, a set of contact details — redefined as fields directly on more than one page content type instead of being modeled once as a reusable content type and linked in.
- **Pass when:** no two or more page content types independently define near-identical field sets for content that represents the same real-world entity (a team member, a testimonial, a product). That content is instead modeled as a single reusable content type (under `ReusableContentTypes/`) and referenced from pages through a linked-item/content-item-reference field. A page-type field that's genuinely page-specific (a hero headline unique to one page) isn't required to be reusable.
- **Severity when failed:** Medium · **Effort:** L · **Fixable:** manual
- **Remediation:** Extract the duplicated fields into a new reusable content type, migrate any existing duplicated data into instances of it, and replace the duplicated page fields with a linked-item reference field pointing at the reusable content type.
- **Reference:** https://docs.kentico.com/guides/architecture/content-modeling/content-modeling-guide/store-content

### AUD-CM-002: Field naming and data types are consistent across content types

- **Inspect:** Field names and data types declared across every `PageContentTypes/*/*.generated.cs` and `ReusableContentTypes/*/*.generated.cs` file. Compare fields that represent the same concept across different content types — a title, a summary, a publish date, a slug, an SEO description.
- **Pass when:** fields representing the same concept use the same name and the same underlying data type on every content type that has one — for example, every content type with a publish date uses the same field name and a `DateTime` type, not a mix of `DateTime` on one type and a formatted string on another. Content types that share a set of fields use a reusable field schema rather than each independently redefining the fields with slightly different names or types.
- **Severity when failed:** Medium · **Effort:** M · **Fixable:** manual
- **Remediation:** Rename the divergent field (regenerating the content type's code afterward) to match the established naming convention, or extract the shared fields into a reusable field schema so future content types inherit one consistent definition instead of redeclaring it. Prefix schema field names with the schema name (the documented convention) to avoid column-name collisions between schemas.
- **Reference:** https://docs.kentico.com/documentation/developers-and-admins/development/content-types/reusable-field-schemas

### AUD-CM-003: Categorization uses taxonomies, not free-text fields

- **Inspect:** Field definitions across all content types for a text or short-text field whose name suggests categorization (`Category`, `Type`, `Tag`, `Tags`, `Group`, `Kind`) and whose data type is a plain string rather than a taxonomy field.
- **Pass when:** every field whose purpose is categorizing or tagging content uses a taxonomy field type (backed by a project-namespaced taxonomy) rather than a free-text string or a comma-separated string field. A free-text field holding a genuinely unstructured label — one never used for filtering, grouping, or navigation — isn't required to be a taxonomy.
- **Severity when failed:** Medium · **Effort:** M · **Fixable:** assisted
- **Remediation:** Create a taxonomy for the values found in the free-text field, migrate the existing string values to the matching taxonomy tags, replace the field with a taxonomy field type, and update any query/filter code that read the old string field.
- **Reference:** https://docs.kentico.com/documentation/developers-and-admins/configuration/taxonomies

### AUD-CM-004: Content hub folders/workspaces organize items (no flat dump)

- **Inspect:** Any code that creates or moves reusable content items (`ArticleContent`, `TestimonialContent`, `TeamMemberContent`, and similar) through the Management API — the folder or workspace path it targets, if any. Also check the CI/CD `repository.config` for whether folder and workspace object types are tracked. Where the audit has access to the deployed Content hub (Management API credentials or a database connection), also check how many reusable content items sit directly at the workspace root versus inside a folder — but treat that as optional supporting evidence, not a requirement for completing this check.
- **Pass when:** **Repo-only criterion (always evaluable, and the only basis for firing this check):** content-creation code that programmatically creates reusable content items (blog admin endpoints, migration/seed controllers, and similar) explicitly places those items into a named Content hub folder rather than leaving them at the workspace root, and the CI/CD repository configuration — when the project uses CI/CD repositories — tracks folder/workspace object types rather than omitting them. **Environment-dependent part (informational only — never fire a finding on this alone):** whether the live Content hub is actually organized into folders, as opposed to a large number of items sitting unfiled at the root, can only be confirmed with Management API or database access. When that access isn't available during the audit, report the live folder organization as "unverified" in the narrative rather than assuming pass or fail.
- **Severity when failed:** Low · **Effort:** M · **Fixable:** manual
- **Remediation:** Add an explicit folder-placement step to any code path that creates reusable content items programmatically — move the item into a named folder as part of the same operation that creates it, rather than leaving it at the workspace root — and track the content-folder object type in the CI/CD repository configuration if the project uses CI/CD repositories. Where Management API or database access is available, audit the item count directly under the workspace root and file the oldest or most numerous types into folders.
- **Reference:** https://docs.kentico.com/documentation/business-users/content-hub/content-hub-folders

### AUD-CM-005: Unused content types are absent or justified (interpret Sentinel CNT001 in context)

- **Inspect:** Sentinel's `CNT001` findings in `report.json` (each names a content type with zero content items). For every `CNT001` finding, search the codebase for evidence the type is deliberately kept despite having no items yet — a feature flag, a template or controller referencing the type that's staged but not yet published, a code comment documenting a planned future use, or a recent creation date suggesting the type hasn't been populated yet. Note: `CNT002` (stale unused reusable content items) is a related but distinct finding — an item with zero inbound references, not a type with zero items — don't conflate the two when interpreting the report.
- **Pass when:** **Repo/artifact criterion (always evaluable once `report.json` is available — this is scan-artifact data Sentinel already computed, not a live probe this audit performs itself):** every `CNT001` finding in the report has a corresponding justification somewhere in the codebase (a referencing code path, a comment, or equivalent evidence the type is intentionally reserved), or the type has genuinely been removed by the time of this audit. A `CNT001` finding with no such evidence anywhere in the repository fails this check. **When `report.json`'s `scan.runtimeEnabled` is `false`** (the scan that produced the artifact ran without a database connection string, so `CNT001` never executed), there's no finding data to interpret — report content-type usage as "not evaluated — static-only scan" in the narrative rather than assuming a pass.
- **Severity when failed:** Low · **Effort:** S · **Fixable:** assisted
- **Remediation:** For each unjustified `CNT001` finding, either delete the unused content type through the Content types application — after confirming with the content owner it's genuinely dead — or add the missing reference/first item so the type is no longer flagged as unused. Document a type's intended future use directly in the codebase (a comment near the type's partial class, or a tracked backlog entry) when it's being deliberately held for later.
- **Reference:** project-convention

### AUD-CM-006: Linked-item structures are bounded (no unbounded/circular reference chains)

- **Inspect:** Every call site retrieving linked/related content items — `WithLinkedItems(depth)` on the Content item query API, or an equivalent recursive-retrieval call — for the depth value passed. Separately, inspect content type field definitions for linked-item/content-item-reference fields that point back and forth between two or more content types (type A references type B, and type B references type A).
- **Pass when:** every call retrieving linked items passes an explicit, small, finite depth — no call uses an unbounded or very large depth value that retrieves everything regardless of actual need — and where two content types reference each other bidirectionally, at least one direction is optional/nullable, or the retrieval code traversing it caps recursion at a depth of one or two rather than relying on the query to stop on its own.
- **Severity when failed:** Medium · **Effort:** M · **Fixable:** manual
- **Remediation:** Set an explicit, small depth argument on every `WithLinkedItems` call based on how deep the view actually needs to traverse, and where a genuinely bidirectional content-model relationship exists, document the intended traversal depth in the repository/service method rather than leaving it to whatever depth happens to be passed at each call site.
- **Reference:** https://docs.kentico.com/documentation/developers-and-admins/api/content-item-api/reference-content-item-query

### AUD-CM-007: Language variants are set up consistently where multilingual is enabled

- **Inspect:** The project's configured languages (`ContentLanguageInfo` seed/migration code, or the Languages application configuration reflected in any tracked CI/CD repository files) to determine whether more than one language is enabled. Where more than one language is configured and the audit has access to the CMS database or Management API, also check how many published content items and pages have a language variant in every enabled language versus only the default — but treat that as optional supporting evidence, not a requirement for completing this check.
- **Pass when:** **Repo-only criterion (always evaluable, and the only basis for firing this check):** if the repository shows only one configured language — no multi-language seed data, no culture-branching code, no tracked language items beyond the default — this check passes trivially, because multilingual isn't enabled and variant consistency doesn't apply. If more than one language is configured, the repository-detectable part of this check passes as long as no code assumes a single hardcoded culture in a way that would break for the additional configured languages (a hardcoded culture string passed to a query instead of the current request's resolved culture, for example). **Environment-dependent part (informational only — never fire a finding on this alone):** when multilingual is enabled, whether content items and pages actually have complete language variants in every enabled language, rather than only the default, can only be confirmed against the live CMS database or Management API. When that access isn't available during the audit, report language-variant completeness as "unverified" in the narrative rather than assuming pass or fail.
- **Severity when failed:** Medium · **Effort:** M · **Fixable:** manual
- **Remediation:** Replace any hardcoded culture assumptions in query or retrieval code with the current request's resolved culture (or an explicit fallback-language configuration), and where database/Management API access is available, audit content items for missing language variants in each enabled language and create them — or configure a fallback language for genuinely optional translations — before treating multilingual support as complete.
- **Reference:** https://docs.kentico.com/documentation/developers-and-admins/configuration/languages

### AUD-CM-008: Widgets present content, they don't store it (structured content stays in content items)

- **Inspect:** Every Page Builder widget property model (`IWidgetProperties` implementations under `Components/Widgets/`) for a property that stores substantial content data directly — a rich-text/HTML blob, a long free-text description, an array of structured sub-items — rather than a reference (a content-item selector field storing a GUID) to a reusable content item.
- **Pass when:** no widget property model stores more than a small amount of presentation-configuration data (a heading override, a layout choice, a CTA label/URL, a display-count limit) directly as a widget property — content meaningful on its own (an article body, a testimonial quote, a product description) is stored in a reusable content item, and the widget only holds a reference to it. A widget property that duplicates a small denormalized display value (a cached title shown while the linked item loads) alongside a reference isn't a fail on its own.
- **Severity when failed:** Medium · **Effort:** L · **Fixable:** manual
- **Remediation:** Move the structured content out of the widget property model into a reusable content type, add a content-item selector property to the widget that references it, and update the widget's view to resolve and render the linked item instead of reading the old inline property.
- **Reference:** https://docs.kentico.com/guides/architecture/content-modeling/xperience-content-modeling-basics/differences-between-structured-content-and-page-builder-content

### AUD-CM-009: URL slugs are clean and former URLs handle renames

- **Inspect:** Any code that generates, rewrites, or redirects page URL slugs — custom slug-generation logic, manual 301 redirect registrations, or Management API calls that patch a page's `urlSlug`. Where the audit has access to the live Channel management configuration or the CMS database, also check whether "Store edited URLs as former URLs" is enabled for the website channel, and sample a handful of published page slugs for cleanliness (no raw GUIDs, no encoded query strings, no double slashes) — but treat that as optional supporting evidence, not a requirement for completing this check.
- **Pass when:** **Repo-only criterion (always evaluable, and the only basis for firing this check):** no code in the repository generates page URLs or slugs in a way that bypasses Kentico's own URL-slug/Former-URL mechanism (a custom redirect table maintained by hand instead of relying on Former URLs, or slug-generation code injecting raw GUIDs or unencoded special characters into the path), and any code patching a page's `urlSlug` through the Management API does so with the documented understanding that Kentico records the prior URL as a Former URL automatically. **Environment-dependent part (informational only — never fire a finding on this alone):** whether "Store edited URLs as former URLs" is actually enabled for the channel, and whether currently published slugs are clean, can only be confirmed against the live channel configuration and CMS database. When that access isn't available during the audit, report both as "unverified" in the narrative rather than assuming pass or fail.
- **Severity when failed:** Low · **Effort:** S · **Fixable:** assisted
- **Remediation:** Remove any hand-maintained redirect logic that duplicates what Former URLs already do automatically, and where channel configuration access is available, confirm "Store edited URLs as former URLs" is turned on for every website channel and spot-check a sample of published slugs for stray GUIDs, encoded characters, or trailing punctuation.
- **Reference:** https://docs.kentico.com/documentation/business-users/website-content/manage-page-urls

### AUD-CM-010: Assets use the current asset model (content item assets), organized in folders

- **Inspect:** Every reference to legacy media-library APIs (`MediaFileInfo`, `MediaLibraryInfo`, attachment-based fields) versus the current content item asset model — an asset field type on a content type, such as a dedicated `Image` content type. For each legacy reference found, check whether it's documented as a known migration item — a code comment, a tracked backlog/TODO entry, or an entry in a migration-tracking doc naming the specific type or field as pending migration to the content item asset model. Where the audit has access to the CMS database or Management API, also check whether asset content items are actually filed into content folders rather than sitting unfiled — but treat that as optional supporting evidence, not a requirement for completing this check.
- **Pass when:** **Repo-only criterion (always evaluable, and the only basis for firing this check):** every use of a legacy media-library API for asset storage is documented as a tracked migration item (a code comment, a backlog/TODO entry, or a migration-tracking doc entry naming the specific type or field slated for migration to the content item asset model). A legacy media-library call with no such documented tracking anywhere in the repository is a fail, regardless of how old the code is — age alone is never the basis for a pass. **Environment-dependent part (informational only — never fire a finding on this alone):** whether asset content items are actually organized into content folders in the live Content hub, rather than accumulating unfiled at the root, can only be confirmed with Management API or database access. When that access isn't available during the audit, report asset folder organization as "unverified" in the narrative rather than assuming pass or fail.
- **Severity when failed:** Low · **Effort:** M · **Fixable:** manual
- **Remediation:** Replace undocumented legacy media-library calls with the content item asset model — an asset field on a dedicated content type, uploaded through the asset upload API. Where a full migration isn't scheduled yet, add a tracked note (a code comment or backlog entry) identifying the specific legacy usage as a planned migration item, so a future audit run recognizes it as accounted for rather than flagging it again. Where Management API or database access is available, move unfiled asset items into content folders grouped by purpose (by article, by product, by page section).
- **Reference:** https://docs.kentico.com/documentation/business-users/content-hub/content-item-assets
